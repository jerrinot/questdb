# Plan: Investigate Java Vector Bytecode vs Native SIMD Performance Gap

Date: 2026-03-28

## Goal

Understand why `JAVA_VECTOR_BYTECODE` is now competitive with
`NATIVE_SCALAR` but still materially slower than `NATIVE_SIMD`, and turn that
understanding into a ranked backlog of concrete optimizations.

This is an investigation plan, not an implementation plan. The purpose is to:

1. identify where time is going
2. determine whether the loss comes from bytecode shape, C2 lowering, or
   fundamental Vector API limitations
3. compare the resulting HotSpot machine code with the native asmjit backend
4. produce a prioritized list of fixes

## Current Benchmark Snapshot

Source: `benchmarks/src/main/java/org/questdb/JitBackendBenchmark.java`

`testFilter` results on the current branch:

| Backend | `l > 42` | `l > 42 AND d < 100.0` | `l IN (1, 2, 3, 4, 5)` | `l > 0 AND i != 0 AND d < 0.5 AND l < 1000000` |
|---|---:|---:|---:|---:|
| `DISABLED` | 808.823 | 964.072 | 631.110 | 1407.383 |
| `NATIVE_SIMD` | 137.930 | 170.305 | 29.115 | 710.201 |
| `NATIVE_SCALAR` | 513.860 | 570.969 | 107.228 | 718.484 |
| `JAVA_BYTECODE` | 551.631 | 550.127 | 154.706 | 656.132 |
| `JAVA_VECTOR_BYTECODE` | 248.977 | 339.395 | 162.120 | not shown |

Immediate observations:

- `JAVA_VECTOR_BYTECODE` is clearly faster than `JAVA_BYTECODE`
- it is now in the same rough band as `NATIVE_SCALAR` for simple filters
- it is still well behind `NATIVE_SIMD`
- `IN()` is especially weak relative to native SIMD
- the mixed predicate `l > 42 AND d < 100.0` still has a large gap, which
  makes mixed-type handling and mask normalization worth special attention

## Questions To Answer

The investigation should answer these questions in order:

1. Is the generated JVM bytecode itself still carrying obvious avoidable work?
2. Does C2 eliminate that work, or does it survive into machine code?
3. Is HotSpot emitting good vectorized machine code for the current bytecode?
4. If not, is the problem:
   - poor bytecode shape
   - helper boundaries blocking inlining/vectorization
   - Vector API lowering limitations in HotSpot
   - row-id compaction overhead
   - mask/species conversion overhead
   - memory access shape
5. Compared to the native asmjit backend, what operations are materially more
   expensive on the Java side?

## Working Hypotheses

These are the main hypotheses worth testing first:

1. **Hot loop shape is still too heavy**
   - repeated `trueCount()`
   - remaining mask casts
   - helper calls not fully disappearing
   - row-id compaction path too expensive

2. **C2 is not lowering the Vector API sequence as efficiently as asmjit**
   - extra moves / spills
   - weaker mask handling
   - weaker compression / store sequence
   - less efficient tail handling

3. **Generated bytecode shape is blocking C2**
   - generic temp locals
   - helper call boundaries
   - insufficient inlining
   - method size or uncommon control flow affecting optimization

4. **Some gaps are fundamental to current HotSpot Vector API**
   - `compress`
   - mask conversions
   - mixed `I8` / `F8` shape
   - `MemorySegment` access path

## Investigation Stages

### Stage 1: Lock Down the Exact Benchmark Cases

Before looking at codegen, fix the exact benchmark targets to inspect:

- `l > 42`
- `l > 42 AND d < 100.0`
- `l IN (1, 2, 3, 4, 5)`
- `l > 0 AND i != 0 AND d < 0.5 AND l < 1000000`

For each case, record:

- selected backend
- selected JIT mode
- whether row-id or count-only path is being measured
- whether the compiled Java path is scalar bytecode or vector bytecode
- whether the filter is pure `I8`, pure `F8`, or mixed

Output of this stage:

- one short matrix mapping benchmark filter -> lowered shape -> backend path

### Stage 2: Review the Generated JVM Bytecode

Start with the generated bytecode before going to machine code.

Tasks:

1. Dump the generated class from `VectorBytecodeFilterCompiler`
2. Disassemble it with `javap -c -p`
3. Inspect the actual `filterRows()` body for the benchmark cases above

Specifically look for:

- loop-invariant work still inside the loop
- repeated `trueCount()`
- repeated `maskCast()`
- redundant `checkcast`
- helper calls that could be inlined into bytecode
- row-id compaction sequence shape
- `MemorySegment` setup and repeated layout loads
- unnecessary loads of constants or species objects

Questions to answer at this stage:

- Does the bytecode look like the intended hot loop?
- Is the current review doc still accurate after examining the actual class?
- Are there obvious source-level codegen improvements that do not require
  machine-code inspection?

Output of this stage:

- a per-filter bytecode review note
- a shortlist of obvious bytecode-shape issues

### Stage 3: Inspect C2 Inlining and Optimization Decisions

Before looking at full assembly, inspect whether HotSpot is even optimizing
the generated methods the way we expect.

Run the benchmark or a focused reproducer with diagnostic options such as:

- `-XX:+UnlockDiagnosticVMOptions`
- `-XX:+PrintInlining`
- `-XX:+PrintCompilation`
- `-XX:CompileCommand=print,...` as needed

Goals:

- verify `filterRows()` is C2-compiled
- verify relevant `FilterHelpers` methods are or are not inlined
- verify Vector API calls stay on the intrinsic path
- detect if method size or profile shape prevents ideal optimization

Things to watch:

- `doubleVecArithmetic`
- `doubleVecEq/Ne/Lt/Le/Gt/Ge`
- `longVecArithmeticNull`
- `longToDoubleNullAware`
- `writeCompressedRows`

Output of this stage:

- inlining status table for the hot methods
- list of helpers that should be inlined but are not

### Stage 4: Inspect HotSpot Machine Code

Once the bytecode and inlining picture are understood, inspect the emitted
machine code for the hot benchmark cases.

Approach:

1. Use HotSpot disassembly for the compiled generated filter methods
2. If `hsdis` is available, use `-XX:+PrintAssembly`
3. If `hsdis` is missing, install it or download it into the local JDK setup
4. Keep the exact JDK build noted in the output

Focus on the machine code for:

- the main loop
- vector loads
- compare/arithmetic sequences
- tail mask handling
- row-id compaction
- stores to the output buffer

Look for:

- extra spills and reloads
- helper calls that survived inlining
- scalarized sections in supposedly vectorized code
- repeated species/mask materialization
- redundant conversions between vector types
- expensive `MemorySegment` access boilerplate

Output of this stage:

- annotated assembly excerpts for the selected benchmark filters
- a list of suspicious instructions or repeated sequences

### Stage 5: Compare with Native Backend Output

Do not stop at HotSpot assembly alone. Compare it directly with what the native
backend emits for the same IR shape.

Reference points:

- native x86 scalar backend
- native AVX2 backend
- serialized IR shape for the same SQL filter

Tasks:

1. identify the native backend path taken for each benchmark case
2. dump or log the generated native code where practical
3. compare loop structure and operation count with HotSpot output

Compare specifically:

- vector load count
- compare/arithmetic instruction mix
- mask creation / use
- tail handling
- row-id compaction / scatter strategy
- branch count
- register pressure and spills

The point is not to force HotSpot to look identical to asmjit. The point is to
understand which extra work on the Java side is real and which differences are
irrelevant.

Output of this stage:

- side-by-side notes: HotSpot vs asmjit for each benchmark case

### Stage 6: Attribute the Gap

After bytecode and assembly inspection, classify each performance delta as one
of:

- **Java codegen issue**
  - can be fixed in `VectorBytecodeFilterCompiler`
- **helper boundary issue**
  - can be fixed by changing `FilterHelpers` or inlining strategy
- **HotSpot limitation**
  - intrinsic or register-allocation limitation
- **Vector API design cost**
  - e.g. mask conversion / `MemorySegment` / `compress`
- **benchmark-path issue**
  - row-id mode overhead dominating the comparison

This stage should end with a ranked backlog:

1. likely high payoff and low risk
2. likely high payoff and medium risk
3. speculative / hotspot-limited

4. **Native comparison**
   - compare pure `I8` vector loop vs AVX2
   - compare mixed predicate loop vs AVX2/native scalar fallback path
   - compare row-id output strategy

## Exit Criteria

This plan is complete when we can answer, with evidence:

1. why `JAVA_VECTOR_BYTECODE` is slower than `NATIVE_SIMD`
2. which part of the gap is in QuestDB-controlled code generation
3. which part of the gap is in HotSpot / Vector API behavior
4. what the top 3 optimization opportunities are
5. whether further work should focus on:
   - bytecode shape
   - helper boundaries
   - row-id compaction
   - mixed-type path
   - HotSpot-specific tuning

## Exit Criteria Answers

1. **Why slower:** The hot loop machine code is near-optimal AVX-512 and
   structurally more efficient per element than native AVX2. The gap comes
   from overhead outside the hot loop: per-call MemorySegment construction,
   IN() column re-loading, safepoint poll, possible AVX-512 throttling.
   No per-cause timing isolation was performed; attribution is structural.

2. **QuestDB-controlled:** IN() column-load deduplication (100%),
   MemorySegment caching or avoidance (100%), I4 column support (100%).

3. **HotSpot/Vector API:** Safepoint poll (JVM), reinterpretInternal too
   big to inline (JDK), AVX-512 throttling (hardware, unconfirmed).

4. **Top 3 optimizations:**
   - IN() column-load deduplication (load column once per chunk)
   - Cache/eliminate MemorySegment construction
   - I4 (INT) column support

5. **Focus areas:** IN() column-load dedup and MemorySegment optimization.
   NOT bytecode shape, helper boundaries, row-id compaction, or HotSpot
   tuning — these are already well-handled.

## Suggested First Pass

The recommended first pass is:

1. inspect generated bytecode for `l > 42`
2. inspect C2 inlining for that same filter
3. inspect HotSpot assembly for that same filter
4. compare it with native SIMD output for the equivalent IR
5. repeat for `l > 42 AND d < 100.0`

That gives the fastest route to understanding whether the current gap is
mostly:

- row-id compaction overhead
- mixed-type overhead
- helper/inlining overhead
- or lower-level HotSpot vector code quality
