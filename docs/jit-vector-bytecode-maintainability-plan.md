# Vector Bytecode Compiler Maintainability Plan

## Goal

Improve the maintainability of
`core/src/main/java/io/questdb/jit/VectorBytecodeFilterCompiler.java`
without degrading:

- generated bytecode shape
- HotSpot C2 inlining / vectorization behavior
- machine code quality
- benchmark results on the existing vectorized filter corpus

This is a refactoring plan, not a redesign of the backend. The IR stays as-is.

## Non-Negotiable Constraints

Every maintainability change must preserve one of these outcomes:

- identical generated bytecode for the hot loop, or
- equivalent / better generated machine code, or
- equivalent / better benchmark results

No refactor should be accepted on readability alone if it changes code shape in
the hot path and cannot be shown to be neutral.

## What To Fix

### High-value maintainability problems

1. `emitMethod(...)` is doing too much.
   It currently combines:
   - local-slot layout
   - setup emission
   - main-loop emission
   - tail-loop emission
   - count-only vs row-ID divergence
   - `StackMapTable` generation

2. The row-ID terminator logic is duplicated.
   The full-chunk and tail-chunk row-ID paths emit nearly the same mask
   reduction, `compress`, writeout, and `filteredCount` update logic.

3. Helper signatures are too wide.
   Emission helpers thread many of the same slot indices, flags, and pool
   references through long parameter lists.

### Medium / low-value cleanup opportunities

4. Program-shape analysis is split across repeated scans.
   `primaryType(...)`, `isPureF8(...)`, and `usesType(...)` overlap.

5. Small local duplication exists in helpers such as `emitLoadVar(...)`.

6. Constant-pool initialization is long and flat.
   This is not a correctness problem, but it can be grouped more clearly once
   the higher-impact work is done.

## What Not To Do

1. Do not introduce a generic “emitter framework”.
   This file is constrained by:
   - exact bytecode order
   - explicit branch positions
   - exact `StackMapTable` frame BCIs
   - JVM verifier behavior

2. Do not refactor via callbacks or lambdas in the core emission path unless
   they materially simplify the bytecode generator.
   A simple helper method is fine. A generalized abstraction layer is likely to
   obscure branch layout and frame placement.

3. Do not treat “fewer source lines” as success.
   The goal is easier reasoning and safer changes, not cosmetic compression.

4. Do not merge count-only and row-ID logic so aggressively that their
   different local layout, reduction strategy, or frame requirements become
   harder to reason about.

## Guardrails

Before and after each non-trivial refactor, compare:

- generated bytecode with `javap -c -p`
- C2 inlining / compilation logs for representative filters
- HotSpot assembly for representative filters when the refactor touches loop or
  terminator emission
- relevant JIT benchmarks

Representative filters:

- `l > 42`
- `l > 42 AND d < 100.0`
- `l IN (1, 2, 3, 4, 5)`
- `l > 0 AND i != 0 AND d < 0.5 AND l < 1000000`

Representative modes:

- count-only
- row-ID output

## Refactoring Strategy

### Phase 1: Safe, Local Cleanups ✅ DONE

These should not affect hot-loop structure.

1. Remove obviously redundant plumbing.
   - replace repeated program scans with a single `ProgramShape` analysis
   - remove the unused `primaryType` plumbing if it is no longer needed

2. Simplify helper internals without changing emitted instruction order.
   - fold duplicated `emitLoadVar(...)` broadcast logic
   - apply similarly small, local cleanups only where emitted bytecode remains
     equivalent

3. Add comments at the actual invariants.
   Useful comments should explain:
   - why `fullMaskSlot` is precomputed
   - why count-only and row-ID differ
   - why frame BCIs are captured exactly where they are

Exit criteria:

- no change in generated bytecode for the representative filters, or a proven
  equivalent shape
- tests green

### Phase 2: Extract Method Structure, Not Semantics ✅ DONE

Split `emitMethod(...)` into coarse-grained helpers with explicit contracts.

Recommended extraction order:

1. `allocateSlots(...)`
   Returns a slot layout object.

2. `emitSetup(...)`
   Emits all pre-loop initialization.

3. `emitCountOnlyLoop(...)`
   Emits the count-only loop and returns loop/tail/exit BCI positions needed
   for stack-map generation.

4. `emitFilterRowsLoop(...)`
   Emits the row-ID loop and returns the same kind of metadata.

5. `emitStackMaps(...)`
   Emits the `StackMapTable` from explicit positions and slot-layout metadata.

The intent is not to unify count-only and row-ID into one generic loop helper
immediately. The first step is to separate concerns while preserving current
code shape.

Exit criteria:

- loop body and branch structure for the representative filters are unchanged or
  neutral by evidence
- stack-map BCIs remain correct
- tests green

### Phase 3: Extract the Duplicated Row-ID Terminator ✅ DONE

This is the best high-impact deduplication target.

Extract a helper for the repeated row-ID terminator sequence:

- finalize the row-result mask
- compute `trueCount`
- skip if zero
- add row base to `iota`
- cast mask for pure `F8` when needed
- `compress`
- `writeCompressedRows`
- increment `filteredCount`

Important:

- the helper should emit bytecode directly into the current method
- it must not hide jump placement
- the caller must still own the `skipBranch` / `tailSkipBranch` labels and BCI
  capture points

This is the right balance between deduplication and verifier safety.

Exit criteria:

- no measurable regression in row-ID benchmarks
- `javap` diff confirms unchanged or equivalent hot-path structure

### Phase 4: Introduce a Minimal Emission Context ✅ DONE

After coarse extraction is stable, replace the worst parameter explosion with a
small immutable context object.

Use a minimal context, not a kitchen-sink bag.

Reasonable contents:

- `BytecodeAssembler asm`
- `Pool pool`
- slot layout
- `tempSlots`
- flags such as `nullChecks`, `pureF8`, `maskedLoads`

Keep op-specific arguments explicit.

Good:

- `emitLoadColumn(ctx, lc)`
- `emitCompare(ctx, cmp)`

Avoid:

- passing both `ctx` and many duplicated slot arguments
- hiding control-flow state in mutable globals

Exit criteria:

- helper signatures shrink materially
- no benchmark or codegen regression

### Phase 5: Program-Shape Analysis Consolidation ✅ DONE (completed in Phase 1)

Replace repeated scans with one analysis pass over the lowered program.

Suggested shape:

```java
record ProgramShape(
        boolean pureF8,
        boolean usesI4,
        int maxColumnIndex
) {}
```

Only include fields that are actually consumed by the compiler.

This analysis should be computed once in `compile(...)` and threaded downward.

Exit criteria:

- compile-time-only simplification
- no change in generated code shape

### Phase 6: Pool Organization Cleanup ✅ DONE

Group constant-pool initialization only after the higher-value work is done.

Suggested internal grouping:

- classes and signature fragments
- `FilterHelpers`
- `VectorSpecies`
- `MemorySegment` and layouts
- vector operators
- per-type vector methods
- row-ID output helpers
- constants

This is a readability pass. It should not be prioritized ahead of loop and
emission-structure work.

## Suggested Supporting Data Structures

### Slot layout

Introduce an explicit slot-layout record or small class.

Example fields:

- `filteredCountSlot`
- `rowSlot`
- `strideSlot`
- `speciesSlot`
- `intSpeciesSlot`
- `nativeOrderSlot`
- `activeMaskSlot`
- `nullVecSlot`
- `outputSegSlot`
- `iotaSlot`
- `matchCountSlot`
- `countAccSlot`
- `fullMaskSlot`
- `colSegSlots`
- `varsSegSlot`
- `tempSlots`
- `maxLocals`
- `objectLocalCount`

This is higher-value than a broad generic `EmitContext`, because slot layout is
the main source of hidden coupling in the file.

### Loop emission result

Return explicit loop metadata from emitted loops.

Example:

```java
record LoopEmission(
        int loopStart,
        int nextStart,
        int tailStart,
        int exitStart
) {}
```

That makes `emitStackMaps(...)` cleaner and reduces accidental coupling between
code emission and frame generation.

## Verification Plan

### Always run

- `mvn -pl core -DskipTests test-compile`
- `mvn -pl core -DforkCount=0 -DreuseForks=false -Dtest=VectorBytecodeFilterCompilerTest,VectorCompiledFilterTest,VectorCompiledFilterIntegrationTest test`
- `mvn -pl core -DforkCount=0 -DreuseForks=false -Dtest=CompiledFilterTest,CompiledFilterRegressionTest test`

### For loop / terminator / frame refactors

Also verify:

- generated class dump via `questdb.jit.vector.dump`
- `javap -c -p`
- HotSpot `PrintInlining`
- HotSpot `PrintAssembly` for at least:
  - `l > 42`
  - `l IN (1, 2, 3, 4, 5)`

### Performance gate

No refactor touching loop emission, terminators, or stack-map logic should land
without checking that the vector-bytecode backend remains at least within noise
for the representative benchmark cases.

## Recommended Order

1. Phase 1: safe local cleanup
2. Phase 2: split `emitMethod(...)`
3. Phase 3: extract row-ID terminator
4. Phase 4: minimal emission context + slot-layout object
5. Phase 5: consolidated shape analysis
6. Phase 6: pool organization cleanup

This order keeps correctness and code quality guardrails strongest around the
parts of the file that directly shape the generated hot loop.

## Success Criteria

The refactor is successful when:

- `VectorBytecodeFilterCompiler.java` is easier to modify without tracing
  dozens of parameters and local-slot conventions manually
- `emitMethod(...)` is no longer the single choke point for all compiler logic
- duplicated row-ID terminator logic is gone
- stack-map generation is explicit and locally understandable
- generated bytecode / machine code quality is unchanged or improved
- representative JIT benchmarks stay flat or improve
