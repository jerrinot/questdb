# Vector Bytecode Gap-Closure Plan

Date: 2026-03-28

Scope:
- `core/src/main/java/io/questdb/jit/VectorBytecodeFilterCompiler.java`
- `core/src/main/java/io/questdb/jit/FilterHelpers.java`
- `core/src/main/java/io/questdb/jit/CompiledFilterIRSerializer.java`
- `core/src/main/java/io/questdb/griffin/SqlCodeGenerator.java`
- `core/src/main/java/io/questdb/jit/IrLowering.java`
- `core/src/main/java/io/questdb/jit/ScalarBytecodeFilterCompiler.java`
- `core/src/test/java/io/questdb/test/jit/*`
- `core/src/test/java/io/questdb/test/griffin/*`

## Goal

Close the remaining practical eligibility gaps in the Java vector bytecode
backend without regressing:

- correctness
- generated bytecode quality for already-supported vectorized cases
- generated machine code for already-supported vectorized cases
- benchmark results for the current fast path

This plan is prescriptive. It is not an exploration document.

## Strategic Position

QuestDB should keep:

- scalar bytecode as the universal Java backend
- vector bytecode as the fast path for eligible straight-line filters

This plan does **not** introduce SIMD short-circuiting.

Short-circuit remains a scalar optimization and a last-effort performance
strategy when SIMD is not in use. It should not block Java vector-bytecode
eligibility for ordinary boolean predicates.

## Non-Negotiable Constraints

### 1. No performance regression for currently supported vectorized cases

The generated bytecode for already-supported vectorized shapes must not
materially change unless a change is backed by equivalent-or-better evidence.

Representative guardrail filters:

- `l > 42`
- `l > 42 AND d < 100.0`
- `l IN (1, 2, 3, 4, 5)`

Representative guardrail modes:

- count-only
- row-ID

Acceptable change standard:

- bytecode unchanged, or
- machine code unchanged/equivalent, or
- benchmark flat or better

### 2. No “scope expansion” refactor that degrades hot-loop clarity

New support must reuse the existing successful loop model:

- full-width unmasked main loop
- masked tail
- direct Vector API operations in the hot path
- helper methods only for semantics that are genuinely awkward to inline

### 3. Do not broaden support by weakening semantics

Any new type/op family must preserve QuestDB semantics for:

- null handling
- epsilon float equality
- div-by-zero behavior
- mixed-type coercion
- bind-var layout

### 4. Do not make `VectorBytecodeFilterCompiler` harder to reason about

All scope expansion must follow the maintainability direction from
[jit-vector-bytecode-maintainability-plan.md](/home/jara/devel/oss/questdb/docs/jit-vector-bytecode-maintainability-plan.md):

- explicit slot/state ownership
- no generic emitter framework
- no opaque abstraction layer over bytecode emission
- preserve verifier and `StackMapTable` clarity

## Explicit Policy Decisions

### 1. No SIMD short-circuiting in this plan

Out of scope:

- vectorized CFG execution
- active-lane short-circuit masking
- chunk-level fast exits for lowered CFG

Reason:

- the remaining non-CFG gaps are practical and high value
- SIMD short-circuit is a separate optimization track with a different cost
  model

### 2. Short-circuit emission must not be triggered by Java backend selection

When the Java backend is configured, `CompiledFilterIRSerializer` must not emit
`AND_SC` / `OR_SC` / `BEGIN_SC` / `END_SC` merely because mixed sizes are
present.

Prescriptive requirement:

- for Java backends, mixed-size detection must no longer imply “emit SC”
- Java vector-bytecode eligibility must be decided by the planner/compiler,
  not preempted by serializer-side scalar-mode assumptions

Practical effect:

- ordinary boolean predicates should reach Java lowering as straight-line eager
  boolean code whenever possible

### 3. Force-scalar remains a testing / guard mechanism

`FORCE_SCALAR` exists for:

- testing
- emergency guard / bug containment

It is not a reason to design the Java fast path around short-circuit IR.

## What Must Be Closed

The remaining practical gaps are:

1. `F4` support
2. `I4` arithmetic / negation / casts
3. `I1` / `I2` via widening to `I4`
4. var-size null-header predicates
5. `I128` / UUID `EQ` / `NE`
6. mixed-width support beyond today’s compare-only subset
7. large straight-line filters blocked by current method-size policy

Out of scope in this plan:

- SIMD short-circuit
- arbitrary CFG vectorization

## Implementation Order

The order is optimized for:

- lowest risk to the current fast path
- highest practical SQL coverage gain
- easiest testing story

### Phase 0: Freeze the Current Fast Path Contract

Before expanding support, lock in the current baseline.

Required artifacts:

- `javap -c -p` dumps for representative currently supported vector filters
- HotSpot assembly snapshots for the same filters
- benchmark snapshots for count-only and row-ID

These become the regression oracle for future scope expansion.

Required benchmark slices:

- `l > 42`
- `l > 42 AND d < 100.0`
- `l IN (1, 2, 3, 4, 5)`

### Phase 1: Fix Serializer Policy for Java Backends

This is the first code change, because it removes an artificial blocker.

Required behavior:

- when Java backend is configured, short-circuit emission must not be enabled
  merely because mixed-size predicates are detected
- Java backends should receive eager boolean IR by default

Required files:

- `CompiledFilterIRSerializer`
- `SqlCodeGenerator`

Required tests:

- serializer-level tests proving mixed-size Java-backend paths do not emit SC
- integration tests proving Java vector backend can see straight-line mixed-size
  predicates

Performance rule:

- this phase must not alter the generated bytecode for the currently supported
  vectorized same-width cases

### Phase 2: Add `F4` Support

This is the highest-value type gap.

Prescriptive implementation rules:

- support `F4` loads, immediates, bind vars, compares, arithmetic, and casts
  using `FloatVector`
- preserve current coercion rules from lowering
- do not special-case `F4` in a way that duplicates the successful `F8` path
  unnecessarily
- where `F4` semantics diverge from IEEE behavior, use helpers in
  `FilterHelpers`

Code-quality rule:

- factor common float-vector semantics cleanly, but do not merge `F4` and `F8`
  code paths so aggressively that bytecode shape becomes opaque

Required tests:

- compare-only `F4`
- arithmetic `F4`
- mixed `I4/F4`
- mixed `I8/F4 -> F8`
- count-only and row-ID
- null-aware float behavior

Performance rule:

- existing `I8/F8` vector bytecode must remain bytecode-stable or
  machine-code-stable

### Phase 3: Add `I4` Arithmetic, Negation, and Cast Support

This closes the most obvious remaining numeric gap.

Prescriptive implementation rules:

- extend `IntVector` support beyond compare-only
- implement `I4` arithmetic with QuestDB null semantics where required
- support `I4` negation
- enable legal `I4 <-> F4` paths only once the `F4` path is in place

Code-quality rule:

- do not create a separate ad hoc `I4` arithmetic engine; extend the current
  typed vector emission model

Required tests:

- `I4` add/sub/mul/div
- `I4` null-aware arithmetic
- `I4` negation
- `I4 <-> F4` casts
- mixed `I4/I8/F8` boolean expressions

Performance rule:

- no extra mask/species traffic may be introduced for the existing `I8/F8`
  path

### Phase 4: Add `I1` / `I2` Through Canonical Widening to `I4`

Do **not** start with `ByteVector` / `ShortVector`.

Prescriptive implementation rules:

- widen `I1` / `I2` to `I4` in the Java vector path
- reuse the `IntVector` execution model
- preserve QuestDB’s arithmetic widening semantics
- keep boolean results normalized into the existing row-mask model

Reason:

- this gives broad SQL coverage with much less backend complexity
- it avoids introducing narrow-lane arithmetic semantics that differ from the
  scalar evaluator

Required tests:

- boolean columns
- byte predicates
- short/char predicates
- arithmetic and compare cases where widening matters

Performance rule:

- no changes to the bytecode shape of existing `I4/I8/F8` filters beyond
  unavoidable support-table growth

### Phase 5: Add Var-Size Null-Header Predicates

This is high-value parity work with contained scope.

Prescriptive implementation rules:

- support only header/null-check use cases
- do not attempt full string/binary/varchar payload SIMD
- keep header loads and comparisons explicit and narrow
- normalize results into the existing boolean/mask model

Supported targets:

- `STRING_HEADER`
- `BINARY_HEADER`
- `VARCHAR_HEADER`

Required tests:

- `string is null`
- `string = null`
- `binary is null`
- `varchar = null`
- row-ID and count-only
- col-top / missing-column cases

Performance rule:

- current fixed-width hot loops must remain unchanged for fixed-width-only
  filters

### Phase 6: Add `I128` / UUID `EQ` / `NE`

This is parity work, not a throughput-first phase.

Prescriptive implementation rules:

- support only `EQ` / `NE`
- do not introduce ordered `I128` comparisons
- prefer a compact lane-wise compare strategy that preserves current semantics
- if full vectorization is awkward, a narrow helper-backed implementation is
  acceptable as long as it remains inside the vector-bytecode backend contract

Required tests:

- UUID column equality
- UUID bind var equality
- null-aware UUID cases if present in current semantics

Performance rule:

- do not complicate the existing fixed-width numeric loop shape to accommodate
  `I128`

### Phase 7: Extend Mixed-Width Support Deliberately

After `F4`, `I4`, and widened `I1/I2` are in, broaden the mixed-width planner.

Prescriptive implementation rules:

- keep the row stride and row-mask model explicit
- extend only combinations that are justified by real SQL coverage
- do not let mixed-width support sprawl into a second backend architecture

Priority combinations:

- `I8 + I4 + F8`
- `I8 + I4 + F4`
- `I4 + F4`

Required tests:

- representative mixed-width boolean chains
- arithmetic + compare mixes
- count-only and row-ID
- mixed null semantics

Performance rule:

- same-width current cases must remain benchmark-flat

### Phase 8: Revisit Large-Method Rejection

Only after semantic gaps are closed.

Prescriptive implementation rules:

- solve method-size overflow by controlled helper splitting or chunking
- do not degrade small/medium hot loops to make huge filters compile
- large-filter support must not penalize the common path

Required tests:

- large synthetic straight-line predicates
- verifier / class-load sanity

## Code Quality Rules

### 1. Extend the current model; do not fork it

Do not create:

- one engine for `F4`
- another for `I4`
- another for var-size

Use the existing typed vector emission model and extend it in place.

### 2. Prefer canonicalization over special-casing

Examples:

- `I1/I2 -> I4` widening instead of direct `ByteVector` / `ShortVector`
- normalized row-mask model instead of type-specific boolean plumbing

### 3. Keep helpers semantic, not structural

Helpers in `FilterHelpers` should be used for:

- null-aware semantics
- epsilon comparison
- awkward conversions
- compact output writes

Do not move ordinary hot-loop structure into helpers just to reduce source code
size.

### 4. Preserve bytecode readability

Generated classes should remain inspectable with `javap`.

Every major expansion must still allow a reviewer to answer:

- where are the loads
- where are the compares/arithmetic ops
- where is the mask reduced
- where does count-only accumulate
- where does row-ID output write

### 5. Use maintainability work to support scope expansion, not replace it

If compiler maintainability improvements are needed for a phase, they should
land only where they make the next support slice safer. Avoid broad cleanup
detours.

## Validation Requirements

### Required tests for every phase

- `mvn -pl core -DskipTests test-compile`
- `mvn -pl core -DforkCount=0 -DreuseForks=false -Dtest=VectorBytecodeFilterCompilerTest,VectorCompiledFilterTest,VectorCompiledFilterIntegrationTest test`
- `mvn -pl core -DforkCount=0 -DreuseForks=false -Dtest=CompiledFilterTest,CompiledFilterRegressionTest test`

If serializer/backend selection changes:

- `mvn -pl core -DforkCount=0 -DreuseForks=false -Dtest=CompiledFilterIRSerializerTest,PropServerConfigurationTest#testSqlJitMode test`

### Required bytecode / codegen validation

For any phase touching existing hot loops:

- dump generated classes
- inspect with `javap -c -p`
- compare representative methods against the Phase 0 baseline

For any phase touching mask/species/loop shape:

- inspect `PrintInlining`
- inspect `PrintAssembly` for representative currently supported filters

### Required benchmark validation

For every scope-expansion phase:

1. rerun the representative current fast-path filters
2. benchmark the newly-supported filter class
3. reject the change if old fast-path performance regresses materially

Representative baseline set:

- `l > 42`
- `l > 42 AND d < 100.0`
- `l IN (1, 2, 3, 4, 5)`

Representative expansion set:

- one benchmark per new type/op family added in the phase

## Definition Of Done

This gap-closure effort is complete when:

- Java vector bytecode accepts all practical non-CFG filter classes:
  - `F4`
  - `I4` arithmetic
  - widened `I1/I2`
  - var-size null-header checks
  - `I128` `EQ` / `NE`
  - important mixed-width numeric combinations
- short-circuit is no longer an artificial blocker for Java backend
  vectorization
- existing currently supported vectorized filters show no material bytecode,
  machine-code, or benchmark regressions
- the compiler remains maintainable enough to inspect and extend without
  obscuring the hot loop

## Recommended Execution Order

1. Phase 0 baseline capture — done (investigation stages 1-5)
2. Phase 1 serializer policy fix — done
3. Phase 2 `F4` — done
4. Phase 3 `I4` arithmetic / casts / negate — done
5. Phase 4 `I1/I2` via `I4` — done
6. Phase 5 var-size null headers — done
7. Phase 6 `I128` — done
8. Phase 7 mixed-width broadening — done
9. Phase 8 large-method support — done (validated, helper splitting deferred)

This order maximizes real SQL coverage while minimizing risk to the currently
fast and already-correct vectorized cases.
