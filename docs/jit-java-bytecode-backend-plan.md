# Plan: Unified Java JIT Backend via Lowering + Bytecode Generation

## Goal

Replace the current split Java execution model:

- scalar interpreter in `VectorFilterInterpreter`
- Vector API executor in `VectorApiFilterExecutor`

with a **single Java backend architecture** built around:

1. decoding the existing QuestDB JIT IR
2. lowering it into a typed internal representation
3. validating that lowered form against the current Java backends
4. generating bytecode as the primary execution path

The immediate purpose of this plan is not to grow the current Java backends any
further. It is to treat them as **learning exercises, semantic references, and
compatibility baselines** while the new lowering + bytecode pipeline is built.

## Why Change the Architecture

The current Java backend started as a simple scalar interpreter, but it has
grown into two substantial runtimes:

- a row-by-row scalar VM
- a type-specialized Vector API engine

This creates pressure in several places:

- scalar and SIMD logic are maintained separately
- type coercion and null semantics are duplicated
- eligibility analysis is separate from execution semantics
- control flow exists in VM form rather than in a directly compilable form

The native asmjit backend avoids some of this because it emits code rather than
executing a generic runtime loop. The Java backend should move in the same
direction: **one compiler pipeline centered on lowering + generated code**.
The current handwritten Java backends have already served their main purpose by
teaching the IR semantics and compatibility surface; they should not be the
primary architectural target from here.

## Design Principles

1. Keep the external QuestDB JIT IR unchanged.
2. Introduce one internal lowered representation and make it the semantic
   center of the Java backend.
3. Treat the existing Java backends as semantic references while migrating, not
   as the architecture to keep extending.
4. Make generated bytecode the primary destination of the lowered form.
5. Keep scalar bytecode as the default execution fallback; Vector API work is a
   later optimization layer, not the first migration target.
6. Make backend selection an implementation detail of one Java pipeline, not a
   split in architecture.
7. Preserve an independent decoded-IR scalar executor as a read-only oracle
   until generated bytecode and any replacement vector strategy are proven.

## Scope

In scope:

- the Java backend architecture
- parity with current Java backend behavior
- parity with native backends as a semantic reference

Out of scope for this plan:

- redesigning the native C++ asmjit backends
- replacing `CompiledFilterIRSerializer`
- changing the external JIT IR format

## Existing Assets To Reuse

These components should be preserved and reused:

- `CompiledFilterIRSerializer`
- `IrDecoder`
- `JitFilter`
- `JitCountOnlyFilter`
- `VectorCompiledFilter`
- `VectorCompiledCountOnlyFilter`
- `VectorFilterInterpreter`
- `VectorApiFilterExecutor`
- `BytecodeAssembler`

The new architecture should sit between `IrDecoder` and the current execution
paths.

## Decisions Fixed Up Front

The following design decisions are fixed before implementation begins:

1. **Type promotion is resolved during lowering, not planning.** The lowered
   form must already encode the promoted operand type, result type, and any
   explicit casts. `Plan` chooses execution strategy only.
2. **Generated scalar bytecode comes before any new vector backend.** If a
   minimal lowered scalar evaluator is introduced during bring-up, it is a
   validation tool only, not the strategic end state.
3. **Vector planning is all-or-nothing initially.** Any later Vector API
   replacement should begin with the current whole-program model. Per-block
   scalar/vector mixing is a later extension.
4. **Short-circuit remains scalar-only initially.** The lowered form should represent
   short-circuit as explicit CFG, but the initial vector planner rejects any
   program with control-flow edges.
5. **Serializer ordering is preserved.** Lowering and planning must not reorder
   predicates initially. In particular, the existing short-circuit predicate
   ordering chosen by the serializer remains authoritative.
6. **Count-only mode is first-class.** The lowered program is shared by both
   row-id and count-only execution. Different execution targets may choose
   different sinks, but count-only is not deferred.
7. **Options are decomposed once.** The packed options word is unpacked during
   decode into a structured form and later stages consume structured fields
   instead of bit-twiddling raw options.
8. **Thread-local working state remains part of the design.** Lowered
   execution and generated bytecode should continue to use reusable per-thread
   scratch state rather than allocating per call.
9. **The decoded-IR scalar executor remains in place during migration.** The
   current decoded-IR path stays available as an independent semantic oracle
   and is not retargeted in place during Phase 3.
10. **Backend-specific memory access stays out of the lowered IR.** The lowered
   form models logical loads only. Scalar backends may use raw pointer access,
   while vector backends may prepare `MemorySegment` wrappers at execution time.
11. **Decoded `executionHint` is binding during migration.** The migrated
    planner may narrow execution further, but it must not widen beyond the
    decoded hint. In particular, `exec_hint == scalar` remains a hard upper
    bound until a later explicit phase changes serializer/backend contracts.
12. **Current wrapper and observability hooks are compatibility surface during
    migration.** `VectorCompiledFilter`, `usesVectorApi()`, and the current
    vector-execution counter semantics should be preserved until tests are
    deliberately migrated away from them.

## Target Architecture

The target Java backend should have four stages.

### 1. Decode

Input:

- serialized QuestDB IR
- options word

Output:

- decoded `Instruction[]`
- decoded options object
- bind-variable byte offsets
- null-check mode
- execution hint
- short-circuit label map

This stage already mostly exists today. The key change is that the packed
options word should be decomposed here into a structured object, for example:

- max column size / logical type size
- execution hint
- debug flag
- null-checks flag

The structured options object is a Phase 1 deliverable, not just a convenience.
During migration, the decoded `executionHint` remains authoritative: planners
may reject vectorization that the hint would allow, but they may not vectorize
programs whose decoded hint does not allow it.

### 2. Lower

Convert the stack-based QuestDB IR into a typed internal representation with:

- explicit temporaries instead of implicit stack slots
- explicit basic blocks instead of VM-style short-circuit opcodes
- resolved operand and result types after coercion analysis
- explicit memory sources for column reads, bind vars, and immediates
- explicit null behavior attached to operations
- explicit count-only sink support

This lowered form does not need to be SSA initially. A typed temporary-based IR
is sufficient.

Concretely, the lowered representation should be:

- a control-flow graph of `LoweredBlock` objects
- each block containing an ordered list of lowered operations
- temporaries addressed by integer IDs, not object references
- a terminator per block (`goto`, `branch`, `return`)

The first implementation should prefer a compact, bytecode-friendly model over
an object-rich SSA design.

The lowered representation must explicitly model the current hard cases:

- **mixed-type promotion**
  - promotions such as `i32 <-> f32` and `i64 <-> f64` are resolved during
    lowering
  - vector species decisions later consume already-promoted types
- **var-size header reads**
  - `STRING`, `BINARY`, and `VARCHAR` header checks should be represented as a
    distinct lowered operation rather than a flavor of generic column load
- **`i128` / UUID**
  - `i128` must be represented explicitly, either as a dedicated value kind or
    as a fixed hi/lo pair with dedicated comparison operations
- **short-circuit control flow**
  - `BEGIN_SC`, `AND_SC`, `OR_SC`, and `END_SC` become explicit CFG edges and
    terminal conditions in the lowered program
- **execution observability**
  - the lowered pipeline must preserve enough information for callers to keep
    reporting whether the vector path was actually selected and executed
- **floating-point compare semantics**
  - float and double comparisons must carry explicit QuestDB semantics,
    including epsilon equality and NaN/null handling, instead of leaving those
    rules implicit in individual executors

### 3. Plan

Analyze the lowered program and choose execution strategy:

- scalar
- vectorizable

For the first implementation, this stage must preserve the current whole-program
model:

- either the entire lowered program is eligible for vector execution
- or the entire lowered program falls back to scalar execution

The initial planner should reject vector execution for programs with:

- short-circuit CFG
- unsupported types
- unsupported var-size header patterns
- unsupported mixed-type combinations
- any shape that current whole-program vector execution cannot represent

Later work may extend this stage to choose per-block execution strategies, but
that is explicitly not the first goal.

This replaces ad hoc eligibility checks inside the current executor split.

The planner should produce an explicit whole-program shape annotation, for
example:

- `SCALAR`
- `I1`
- `I2`
- `I4`
- `I8`
- `F4`
- `F8`
- `MIXED_I4_F4`
- `MIXED_I8_F8`

This annotation is the bridge from lowered semantics to the species-specific
Vector API implementation.

The planner must also respect decoded `executionHint` as a hard upper bound for
the entire migration:

- `scalar` means scalar only
- `single-size` means vectorization is permitted if all other planner checks
  pass
- `mixed-size` remains non-vectorizable in the first planner

Any future phase that allows Java to outsmart the serializer must be an
explicit contract change, not an accidental side effect of the migration.

### 4. Validate / Generate

The lowered program should support multiple execution targets:

- generated bytecode executor
- unchanged decoded-IR scalar oracle
- optional minimal lowered scalar validation executor
- optional later Vector API replacement

Each execution target must support both:

- row-id filtering
- count-only filtering

The first new execution targets should be:

- a generated scalar bytecode executor
- an unchanged decoded-IR scalar oracle for parity checks

Any new handwritten lowered executor should be justified as a validation tool,
not as the main destination of the architecture.

Execution targets should also preserve the existing no-allocation calling model
by using reusable thread-local working state.

During migration, the fallback chain should be explicit:

- generated bytecode executor, when coverage exists
- unchanged decoded-IR scalar oracle
- optional lowered validation executor, only if introduced for debugging or
  incremental bring-up

If lowering or code generation cannot handle a program yet, that is a migration
gap and should fall back to the decoded-IR scalar oracle until the gap is
closed.

The migration should also preserve the current test-facing compatibility
surface:

- compiled-filter wrappers remain `VectorCompiledFilter` /
  `VectorCompiledCountOnlyFilter` unless and until tests are deliberately
  updated
- `usesVectorApi()`-style observability remains available
- the current vector-execution counter semantics remain available to test
  helpers

## Migration Strategy

The migration should be incremental and testable at each step.

### Phase 1: Introduce the Lowered Representation

Add new internal classes for a lowered Java backend, for example:

- `LoweredProgram`
- `LoweredBlock`
- `LoweredOp`
- `LoweredValue`
- `LoweringContext`

Responsibilities:

- represent typed operations directly
- encode control flow explicitly
- represent var-size header reads explicitly
- represent `i128` explicitly
- define the structured decoded-options object
- carry enough metadata for count-only execution and observability
- preserve enough source metadata for debugging and tests

Validation:

- lowering unit tests that compare lowered shape against decoded IR
- no change to runtime behavior yet

### Phase 2a: Core Lowering From Existing Decoded IR

Build an initial lowering pass from `IrDecoder.Instruction[]` into
`LoweredProgram` for the straight-line fixed-width subset.

The initial lowering pass should handle:

- `IMM`
- `MEM` for fixed-width types
- `VAR`
- `NEG`
- `NOT`
- boolean ops
- comparisons
- arithmetic
- `RET`

It should also encode:

- coerced result types
- promoted mixed-type operations
- bind-var offsets
- null-check behavior

Validation:

- direct tests for fixed-width lowered shapes
- mixed-type coercion tests
- comparison and arithmetic tests

### Phase 2b: Complete Lowering

Build a lowering pass from `IrDecoder.Instruction[]` into `LoweredProgram`.

Extend lowering to handle the remaining hard cases:

- short-circuit blocks
- var-size header reads
- `i128` / UUID comparisons
- count-only sink metadata

It should also encode:

- exact CFG for short-circuit semantics
- preserved serializer ordering
- observability data for selected execution path
- enough wrapper metadata to preserve current test-facing observability hooks

Validation:

- direct tests for tricky lowered shapes
- chained `IN` IR patterns
- mixed-type coercions
- var-size null checks
- `i128`
- short-circuit CFG tests

### Phase 3: BytecodeAssembler Feasibility Spike

Before committing to full bytecode generation, build a small end-to-end spike
that proves the current `BytecodeAssembler` is adequate.

The spike should generate a minimal class that:

- implements `JitFilter`
- emits a real loop and at least one conditional branch
- delegates part of the work to helper methods
- stays within practical JVM method-size limits
- does not require unmanageable StackMapTable maintenance

This phase determines whether Phase 4a is "generate bytecode" or "extend
BytecodeAssembler, then generate bytecode."

Validation:

- generated class loads and executes correctly
- method-size and frame-management constraints are understood
- no hidden blocker remains in class emission infrastructure

### Phase 4a: Introduce a Generated Scalar Bytecode Executor For the Core Subset

Generate scalar bytecode from `LoweredProgram` for the Phase 2a straight-line
fixed-width subset.

The first bytecode executor should be conservative:

- start with scalar code generation only
- use helper methods for complex operations
- avoid generating huge monolithic methods
- keep `call()` itself small and delegate to generated or handwritten helpers
- preserve `JitFilter` / `JitCountOnlyFilter` contracts exactly

The generated class should implement the same runtime contract as `JitFilter`
and `JitCountOnlyFilter`.

The generated code must account for practical JVM limits:

- seven-`long` `call(...)` signatures for row-id mode
- six-`long` `call(...)` signatures for count-only mode
- pointer arithmetic for column and bind-var access
- loop structure and memory writes without exceeding huge-method limits
- reusable per-thread scratch state

Validation:

- compare bytecode executor results against the unchanged decoded-IR scalar
  oracle
- fixed-width focused tests
- mixed-type fixed-width tests
- representative performance checks against the decoded-IR scalar oracle

### Phase 4b: Complete Generated Scalar Bytecode Coverage

Extend generated scalar bytecode to cover the full lowered language:

- short-circuit CFG
- var-size header checks
- `i128`
- count-only execution
- full broad-suite semantic coverage

The decoded-IR scalar executor still remains in place after this phase for
independent parity checks.

Validation:

- `CompiledFilterTest`
- `CompiledFilterRegressionTest`
- compare bytecode executor results against the unchanged decoded-IR scalar
  oracle
- focused tests for short-circuit and null semantics
- representative performance checks against the decoded-IR scalar executor

### Phase 5: Optional Vector Replacement Work

Only after scalar bytecode generation is complete should vector work resume.
At that point, choose one of two directions explicitly:

- a lowered whole-program Vector API executor for the current straight-line
  subset
- a bytecode-driven strip-mined scheduler that invokes Vector API kernels

This phase is optional in the sense that scalar bytecode is the primary
architectural goal; vector work is a later optimization layer.

If a lowered whole-program Vector API executor is pursued first, it should
match the current whole-program model:

- straight-line programs only
- one monomorphic vector shape for the whole program
- no scalar/vector region switching
- explicit planner-produced shape selection for `I1`, `I2`, `I4`, `I8`, `F4`,
  `F8`, `MIXED_I4_F4`, and `MIXED_I8_F8`

Memory access remains backend-specific here:

- the lowered IR describes logical loads
- the vector execution path prepares `MemorySegment` views or equivalent
  execution state from the raw `long` addresses passed into `call(...)`
- those details do not become part of the lowered IR itself

Validation:

- existing vector path tests
- integration tests proving actual Vector API execution
- parity checks against generated scalar bytecode
- parity checks against the unchanged decoded-IR scalar oracle
- representative performance checks against the current Vector API path for the
  supported subset
- compatibility checks for current wrapper identity and execution-counter hooks

### Phase 6: Optional Hybrid Bytecode + Vector Scheduling

If vector replacement work begins, evaluate whether hybrid execution is
worthwhile.

If pursued, this phase must introduce an explicit strip-mined scheduling model
rather than treating Vector API work as simple scalar leaf helpers. The hybrid
model would need a scheduler that owns:

- the outer chunk loop
- vector-width step selection
- active-lane mask handling
- row-id compaction or count accumulation
- scalar tail execution

Only within that scheduling model should generated bytecode delegate to Vector
API kernels.

This means Phase 6 is a separate design step, not a direct extension of the
first bytecode executor.

Validation:

- existing vector tests
- actual-path assertions
- semantic parity against scalar bytecode

## What The First Bytecode Version Should Not Do

The first bytecode generator should not attempt all of the following at once:

- direct generation from the current stack IR
- full Vector API emission inline in generated bytecode
- elimination of the current interpreter before parity is proven
- aggressive whole-program fusion into one large generated method

That approach would move current complexity into a harder-to-debug form without
first improving the architecture.

## Recommended Internal Shape

The lowered program should model operations such as:

- `LoadColumn`
- `LoadVarSizeHeader`
- `LoadVar`
- `LoadImm`
- `Cast`
- `Compare`
- `CompareI128`
- `Arithmetic`
- `Boolean`
- `Negate`
- `BranchIfTrue`
- `BranchIfFalse`
- `Return`

Each lowered value should know:

- exact type
- nullable vs non-nullable behavior
- fixed-width vs var-size-header semantics
- vector eligibility

This information should be computed once and then reused by all execution
targets.

The lowered program should also preserve:

- promoted common types for mixed-type expressions
- count-only execution intent
- whether the program has CFG and is therefore scalar-only in the first planner
- enough metadata to preserve `usesVectorApi()`-style observability

A concrete sketch is:

```java
final class LoweredProgram {
    DecodedOptions options;
    ObjList<LoweredBlock> blocks;
    int entryBlock;
    boolean countOnly;
}

final class LoweredBlock {
    int id;
    ObjList<LoweredOp> ops;
    Terminator terminator;
}

sealed interface LoweredOp permits
        LoadColumnOp,
        LoadVarSizeHeaderOp,
        LoadVarOp,
        LoadImmOp,
        CastOp,
        CompareOp,
        CompareI128Op,
        ArithmeticOp,
        BooleanOp,
        NegateOp {
    int dst();
}

sealed interface Terminator permits GotoTerm, BranchTerm, ReturnTerm {}
```

This is not meant to freeze exact class names, but it does freeze the important
shape:

- CFG, not a flat instruction array with markers
- integer temporary IDs
- explicit terminators
- explicit lowered operations for the non-generic cases

## Testing Strategy

The current Java backends should remain available during migration and should be
treated as test oracles.

For each migration step, compare:

- decoded-IR scalar execution vs generated bytecode execution
- generated scalar bytecode vs any later vector replacement work
- generated bytecode execution vs current compatibility hooks and wrapper
  behavior

The decoded-IR scalar executor must remain available until those comparisons are
no longer needed. It is the only fully independent Java oracle during the
migration.

Broad existing suites should continue running throughout:

- `CompiledFilterTest`
- `CompiledFilterRegressionTest`

Focused tests should cover:

- short-circuit programs
- chained `IN` IR patterns
- null semantics
- mixed-type coercions
- var-size null checks
- UUID bind vars
- count-only filters

Observability should be preserved throughout migration:

- callers must still be able to tell whether the vector path was selected
- tests should continue asserting actual vector-path execution where expected
- current test-facing wrapper identity and execution-counter hooks should remain
  valid until a deliberate compatibility-change phase updates those tests

## Performance Gates

Semantic parity is the primary goal, but each major phase should also clear a
basic performance gate before the legacy implementation is retired.

- After Phase 4b:
  no material regression vs the decoded-IR scalar executor on representative
  filter workloads.
- After Phase 5:
  no material regression vs the current Vector API path for the supported
  straight-line subset, if vector replacement work is pursued.

The exact threshold should be chosen before implementation starts and measured
with either existing JMH benchmarks or a representative dedicated filter
benchmark corpus.

## Role of BytecodeAssembler

`BytecodeAssembler` is a useful starting point, but it should be treated as
infrastructure, not as the architecture.

Use it to bootstrap:

- generated classes
- small generated methods
- helper method invocation
- branch-based control flow

Generated classes should implement the existing filter interfaces, but the
generated `call()` methods should remain thin entry points. Complex loops and
helper logic should be split into separate generated methods or handwritten
helpers to stay within JVM method-size limits.

Expect follow-up work if needed for:

- richer generated method shapes
- modern class-definition strategy
- improved ergonomics for complex code generation
- StackMapTable and control-flow tooling if the feasibility spike shows gaps

## First Concrete Deliverable

The first concrete deliverable under this plan should be:

**A lowered-program pipeline plus a successful bytecode feasibility spike,
alongside the unchanged decoded-IR scalar oracle.**

That is the narrowest step that proves the architecture is viable.

Once that is working:

- the lowered form becomes real
- bytecode generation becomes the next concrete implementation step
- the decoded-IR scalar executor remains available for independent parity checks
- current handwritten Java backends remain reference implementations rather than
  growth targets

## Legacy Removal

After generated scalar bytecode is proven, add a cleanup phase to remove the
legacy handwritten scalar executor. Any legacy Vector API path should remain
only until an explicit replacement strategy is implemented or intentionally
deferred.

Removal criteria:

- broad existing suites green on the new pipeline
- parity checks against the decoded-IR oracle complete
- performance gates met
- no remaining legacy-only edge cases

Only after those conditions are met should the decoded-IR scalar executor stop
being preserved as a migration oracle.

## Success Criteria

This plan is succeeding when:

1. the Java backend has one semantic center: the lowered program
2. generated scalar bytecode becomes the primary Java execution path
3. the current handwritten Java backends stop growing and are used only as
   references until removal
4. any later vector work derives from the same lowered form rather than from a
   separate handwritten architecture
5. broad existing JIT suites remain green throughout the migration
6. legacy executors are removed once parity and performance criteria are met
